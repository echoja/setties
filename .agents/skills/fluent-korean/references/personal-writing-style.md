# 산출물 글쓰기 스타일

독자와 공개 여부에 관계없이 문서에 적용한다. 이슈, 초안, 보고서, 내부 메모, 규칙문서도 포함한다. [표현 예시](writing-examples.md)는 문장을 다듬을 때 참고한다. 한국어 문장에는 fluent-korean 지침도 함께 적용한다.

규칙문서를 작성하거나 수정할 때는 정본 `META_RULE`을 우선한다. 응답 언어, 파일 링크, 검증 결과 보고, 원문 보존, 작업 기록 방식은 현재 설정을 따른다. 사용자의 할 일 이름과 고유 명칭을 문체 교정만을 위해 바꾸지 않는다. 이 문서는 Git 작업이나 외부 동기화의 권한을 바꾸지 않는다.

- 일반 설명은 도메인 이름으로 쓴다. 코드 위치를 알아야 검토하거나 수정할 수 있으면 현재 규칙에 따라 파일 링크와 필요한 줄 번호를 제공한다. Basana 파일 링크에는 줄 번호를 넣지 않는다.
- 기술 문서에서 화면을 식별해야 하면 실제 화면 이름, URL path, 컴포넌트 파일 이름을 사용한다. 이름을 임의로 만들지 않으며, 사용자 흐름에는 구현 경로를 불필요하게 노출하지 않는다.
- 산출물 본문에는 불필요한 메타 정보를 넣지 않는다(예: 작업 브랜치, 작성자 상태). 일정 날짜, 진행 기록, 검증 결과처럼 문서 목적에 필요한 정보는 남긴다.
- 중의적인 말 대신 명확하고 직설적으로 쓴다.
- 같은 의미의 규칙은 한 곳에 두고, 수행할 행동을 긍정문으로 명시한다.
- 직접적인 기술 용어를 쓰고 비유, 은유, 메타포는 사용하지 않는다.
- 간결하게 쓰되, 용어가 뭉뚱그려진다면 풀어서 설명한다.
- 짧은 예시와 보충 설명은 괄호 안에 넣는다. 문장으로 설명할 내용은 별도 문단으로 쓴다.
- 괄호 안이 예시이면 `예: ` 로 시작한다. (`(예: example-test.com)`)
- 산문에서 항목을 잇거나 구분할 때 빗금(`/`), 가운데점(`·`), 더하기(`+`)를 쓰지 않는다. 쉼표, `및`, `와`, `과` 로 잇는다. (코드, 경로, 버전 표기 안의 기호는 예외)
- 새 문서는 처음부터 길게 쓰지 않고 전체 윤곽(소제목 등)을 먼저 잡은 뒤 점진적으로 채운다.
- `존재` 라는 단어를 쓰지 않는다. `있다`, `없다` 로 쓴다.
- PR 번호와 이슈 번호는 문서에 나올 때마다 해당 PR 이나 이슈로 링크를 단다.
- 링크는 백틱으로 감싸지 않는다. Markdown 링크를 사용하며, 현재 파일에 URL을 그대로 적는 형식이 정해져 있으면 그 형식을 따른다.
- 관계를 서술어로 끝낼 수 있다면 그렇게 한다. 특히 `~기준`, `~측면`, `~차원`, `~부분`, `~관련` 처럼 관계의 자리만 가리키고 내용은 비운 명사구로 끝나면, 그 관계를 서술어로 푼다.
- 숨은 주어는 사람(작성자 측)으로 읽히게 쓴다. 행위자가 시스템이면 한 번 명시하고 그 뒤로 숨긴다.
- 표준 기술 용어(주로 영어)가 어설픈 번역어보다 나으면 그대로 쓴다. 예: `본문` 은 뜻이 너무 넓고 맥락에도 안 맞아 `body` 로 쓴다.
- `단언` 이라고 쓰지 않고 `Assertion` 으로 쓴다.
- `가져오기` 라고 쓰지 않고 `import` 로 쓴다.
- URL 쿼리 파라미터 값을 `질의값` 이라고 쓰지 않고 `searchParams 값` 으로 쓴다.
- API 의 주소를 `경로` 라고 쓰지 않고 `endpoint` 로 쓴다. URL 의 경로 부분만 가리킬 때는 `path` 로 쓴다.
- `부품` 이라고 쓰지 않고 `컴포넌트` 로 쓴다.
- `고치다` 라고 쓰지 않고 `수정하다` 로 쓴다.
- `결정 기록` 이라고 쓰지 않고 `ADR` 로 쓴다.
- 비즈니스를 가리킬 때 `업무` 라고 쓰지 않고 `비즈니스` 로 쓴다. (`업무 맥락` 대신 `비즈니스 맥락`)
- `머리말` 이라고 쓰지 않고 `Header` 로 쓴다.
- git 브랜치를 `가지` 라고 쓰지 않고 `브랜치` 로 쓴다. (`기준 가지` 대신 `base 브랜치`)
- `잠금`, `열림` 이라고 쓰지 않고 `편집 불가`, `편집 가능` 으로 쓴다.
- `보여 준다`, `숨긴다`, `띄운다`, `그린다` 라고 쓰지 않고 `노출`, `미노출` 로 쓴다.
- 문서가 주어인 자리에 `담는다` 를 쓰지 않고 `다루는 것` 또는 `설명한다` 로 쓴다.
- 수량을 밝히는 자리는 한글 수사 대신 아라비아 숫자로 쓴다. (`여섯 종` 대신 `6종`, `기준은 넷이다` 대신 `기준은 4개다`) 수량이 아니라 방식을 가리키는 자리는 한글로 둔다. (`한 번`, `둘로 나눈다`, `둘 중 하나`)
- 코드에 이름이 있는 용어는 원어로 쓴다. `store`, `getter`, `setter`, `action`, `props`, `emit`, `composable`, `interceptor` 가 여기에 든다.
- 루트 repo 의 개인 로컬 파일과 그 경로는 외부로 나가는 문서(PR 본문, 이슈 등)에 언급하지 않는다.
- 두괄식으로 쓴다. 요청, 결론, 결정을 배경과 근거보다 앞에 둔다. (메신저 요청 메시지 포함)
- 도입 문장은 뒤따르는 표나 목록에 없는 정보만 담는다.
- 목록은 성격이 같은 항목을 나열할 때만 쓴다. 성격이 다른 설명, 조건, 이유, 예외는 문단으로 쓴다.
  - 비교하거나 순서대로 실행할 항목은 목록으로 쓴다. 설명과 인과관계는 문단으로 쓴다. 별도 개수 기준이 있는 프로젝트에서는 그 기준을 따른다.
  - 목록을 여는 도입 문장에서 항목 개수를 세지 않는다. `다음과 같다` 로 쓴다.
  - 목록의 항목은 같은 성격끼리 묶고 형태를 맞춘다.
  - 나열하는 항목은 명사형으로 맞춘다. 규칙, 조건, 인과관계는 의미가 분명한 문장으로 쓴다.
  - 목록을 여는 도입 문장이 뒤 내용을 가리키기만 하면 `이름:` 형태의 라벨로 쓴다.
  - 목록 항목이 이름과 설명으로 나뉘면 쌍점(`:`)으로 잇는다. 줄표(`—`)는 쓰지 않는다.
  - 목록 기호는 `-` 를 쓰고 하위 단계마다 공백 2칸으로 들여쓴다. `•`, `◦` 는 쓰지 않는다. (메신저 메시지 포함)
- 반복되는 동작은 술어명사로 고정하고 문서 전체에서 같은 이름을 쓴다. 시스템에 이미 이름이 있으면 그 이름에 맞춘다. 목록과 표와 제목은 명사로 끝내고, 규칙과 근거는 문장으로 쓴다.
- 열이 하나뿐인 표는 쓰지 않고 목록으로 쓴다.
- markdown 문서에서 제목, 문단, 목록 사이에는 빈 줄을 하나씩 둔다.
- 제목을 `~것` 으로 끝내지 않는다. (`점검할 것` 대신 `연동된 설정`)
- 산출물 본문에서 변경과 무관한 환경 문제를 나열하지 않는다. 검증 결과나 완료 판단에 영향을 주는 실패와 한계는 보고한다.
- 현재 동작의 근거로는 유효한 문서를 사용한다. deprecated 문서를 과거 동작의 근거로 쓸 때는 해당 범위를 명시한다.
- 메신저(Slack 등) 메시지 링크 옆에는 그 메시지의 날짜를 적는다. (`https://example.slack.com/archives/... (2026-07-06)`)
- 문서 안의 다른 섹션을 가리킬 때는 그 제목의 앵커 링크로 `[섹션 이름](#앵커) 섹션` 이라고 쓰고, 그 섹션에서 무엇을 보면 되는지 함께 적는다.
- 환경을 묶어 부를 때는 `prod`, `non-prod` 로 쓴다. `운영`, `비운영`, `상용`, `live` 로 쓰지 않는다.
- 조사 과정(검색 조건, 집계 수치, 로그 링크, 데이터를 확인한 방법과 시점)은 문서에 적지 않고 보고에만 쓴다. 문서에는 결론과, 결정이나 논의를 담은 근거 링크만 적는다.
- 통상적인 작업 절차는 적지 않는다. 결과와 고려사항을 적는다.
- 변경 파일 목록에는 검토에 필요한 파일을 포함한다. 테스트 파일과 검증 근거의 보고 여부는 현재 작업 규칙을 따른다.
- 배경과 근거는 지난 경과가 아니라 조건과 결과로 쓴다. 특정 사건은 예시로 괄호 안에 둔다.
